# Phase 2 — cluster review: domain + store + config (reviewer report, condensed; delivery was truncated at the top — the HIGH findings were requested again and are recorded in phase2-claude-response.md)

## MEDIUM (as delivered)
- Password-hash shape: `people_have_hashes: … occurrences ('$') = 2` accepts `"a$b$c"`; a corrupted or hand-edited row is accepted by the domain and fails later inside PASSWORD_HASHER.verify/iterations_of on the login path → `PASSWORD_HASHER.is_pbkdf2 (a_hash)` (three parts, 32-hex salt, iterations ≥ Minimum_iterations, 64-hex digest) in `make`, `set_password_hash` and the invariant.
- `CHAT_ATTACHMENT.original_name` unconstrained (path separators, controls, unbounded; shown in the UI and the natural `Content-Disposition` value; chat_attachment.e 43, chat_json.e 201-205) → `name_shape` (≤ 255, no separators, no controls); basename on upload; Void on decode.
- Exported mutable strings carry the invariants — `e.body.wipe_out` after append breaks `marked_when_bot`; `u.username.append` breaks `username_shape`; events are shared by reference between store, bus, streams and participants; `payload` goes into outgoing JSON by reference (chat_event.e 57/59, chat_user.e 50-56, chat_session.e 41, chat_attachment.e 43-47, chat_member.e 37-38, chat_room.e 31, chat_error.e 35-40, chat_status.e 34-35, participant_config.e 68, server_config.e 87-90, chat_json.e 44) → IMMUTABLE_STRING_* / READABLE over private copies; `payload` as a copy; stores return twins.
- SERVER_CONFIG/PARTICIPANT_CONFIG export mutable lists (`participants`, `validation_errors`, `aliases`, `allow_via`) — `fresh_*` preconditions bypassable, `is_valid` flippable → `{NONE}` + counted accessors.
- `make_from_file`'s postcondition is a tautology (`is_valid or not validation_errors.is_empty` with `is_valid = validation_errors.is_empty`); invalid values cannot be represented so defaults silently stand in → `loaded: BOOLEAN`, `loaded_or_explained: loaded = is_valid`, `errors_name_fields`; the facade refuses to start on `not is_valid`.
- `public_name` and DDNS fields spliced into generated files with no shape check (Caddyfile injection via `"x {\n reverse_proxy evil:1"`) → `is_hostname`, per-domain validation, `known_provider`.
- Uniqueness stops at handles — bot usernames and aliases can collide across participants; aliases not lowercased → `unique_bot_usernames`, `unique_addresses` (handles + aliases, lowercased).
- Kind-specific engine requirements are not invariants (`set_engine` has no precondition) → `engine_for_kind`, `is_known_shaper`.
- A database written by a newer build crashes `version_of` (`never_ahead` postcondition) instead of being refused → drop `never_ahead`; `open` refuses with `last_error`.
- One CHAT_JSON with a mutable `parser` shared by every handler thread (chat_json.e 349, chat_api.e 144) → parser as a local; CHAT_JSON stateless and shareable.

## LOW (as delivered)
Attachment may ride on a message/system event (`attachment_only_on_images` missing); CHAT_EVENT_DRAFT's invariant states 2 of its 6 rules; validation predicates and constants duplicated (CHAT_EVENT vs CHAT_EVENT_KINDS, CHAT_USER vs CHAT_USER_RULES, CHAT_ATTACHMENT vs CHAT_ATTACHMENT_RULES); creation postconditions omit arguments (created_at, attachment, payload, expires_at, …); domain setters have no frames; memory-store frames uneven and the invariant calls `event_count` whose precondition `is_open` does not hold after `make`; constants aliased into mutable attributes (`front_door_kind := Door_none`, `query_shaper := Shaper_none` — `append` would mutate the once-object); SQLITE_CHAT_STORE `lock_attached` tautology + MUTEX recursion assumption; wire attachment accepts id 0 and fabricates uploader/time (dropped for system events); `page_from_bytes` ignores `last_id`, tolerates malformed statuses one by one while refusing events whole, no same-room check; `CHAT_ERROR.code` unrestricted, documented list stale; weak/missing postconditions on `mention`, `ai_enabled`, `has_participant_handle`, `allows_via`, `has_alias`, `count_after`; `CHAT_STATUS` from/text unvalidated and unbounded; session flags/ownership not tied to the user (`put_session` overwrites another user's session with `updated` semantics); room names bounded by count only; `has_participant_handle` case-sensitive while handles are lowercased and `still_unique` checks presence; display-name length counted in code points here and possibly bytes on SQLite read-back (`require decoded`); CHAT_RESULT unsatisfiable for detachable/expanded G (latent; constrain `G -> ANY`).

## INFO
A person can post a message starting with the marker (implication one-way — render from `is_bot`, never from the glyph); design choices to confirm at the gate: a bot may be admin; `CHAT_MEMBER` carries no `is_active` (deactivated users appear in rosters and can be addressed); `events_since` has no page maximum in the store; `CHAT_STORE.open` can only raise on failure; no attachment dedup by sha256; time-zone fidelity of `to_iso8601` round trip; `localhost_only` effectively a constant; schema note lacks UNIQUE on `user.username`/`membership`. Assault gaps: uppercase/non-hex sha256, `../` inside sha256, empty error message, non-error status into `error_from_bytes`, unparseable `created_at`, non-Latin-1 in kind/username/token, attachment on a message event, negative `sender_id` on a system event, duplicate memberships, gaplessness of `events_since`, recency of `events_before`, `update_user` with a changed username, mutation of a store-returned CHAT_USER.
