# Phase 2 — cluster review: service + bus + web + facade + door (reviewer report, condensed; every finding cites file + line as delivered)

## HIGH (15)
1. **POLL_WAITER.wait's postcondition is evaluated after the lock is released** — poll_waiter.e 96-99: `Result := wakes_since_arm > 0` / `lock.unlock` / `definition: Result = (wakes_since_arm > 0)`. A wake landing between the unlock and the postcondition falsifies it; same for `wake`'s `mine_counted` (124) and inherited `counted` (event_subscriber.e 38): `old` captured before `lock.lock`, compared after `lock.unlock`; two posters ringing the same room fail `2 = 0 + 1`. A wake that raises is unsubscribed by the bus → one race kills the poller for the request. Body is correct; contracts are wrong. → keep the thread-stable direction only: `Result implies wakes_since_arm > 0`; `counted: wake_count > old wake_count`; drop `mine_counted`/`others_ignored`/`kept_when_mine` (single-threaded Phase 5 tests).
2. **Exact "+1"/"unchanged" postconditions on thread-shared state are unsatisfiable under EWF threads (systemic)** — chat_service.e 105-108 (`appended_on_success`, `rung_on_success`, `nothing_on_failure`), post_image 126-129, publish_status 153-154, authenticate 69; event_bus.e 83, 92; chat_log.e 30/37/44; rate_limiter.e 111, 101, 121-122; stream_sink.e 35; chat_store.e 84/88 (`is_last`, `one_more`), 113 (`contiguous`); memory_chat_store.e frames 148-153, 203-206. `old` is captured before any lock and the postcondition runs after every lock is released; CHAT_SERVICE holds no lock and its postconditions span three locks — the only way both `appended_on_success` and `rung_on_success` hold is a service-wide lock across `bus.ring`, which the lock order forbids, and even that would not help. Poster A captures old 7, B appends 8, A appends 9 → `9 = 7 + 1` fails. `contiguous` in `events_since` fails whenever an append lands between the query and `count_after`. The memory store's `|=| old` frames will fire spuriously under `test_doorbell_no_loss_under_concurrency`. These contracts are right only if the objects are SCOOP `separate`. → decide the concurrency model once: under threads use monotone forms (`e.id > old store.last_event_id and store.last_event_id >= e.id`; `ring_count > old ring_count`; `lines_written > old`; `is_last: last_event_id >= Result.id`; `one_more: event_count > old`; `contiguous: … <= count_after`), drop `nothing_on_failure`, state RATE_LIMITER frames single-threaded only; exact arithmetic lives in single-threaded Phase 5 tests. Alternatively declare EVENT_BUS, RATE_LIMITER, POLL_WAITER, CHAT_LOG and the stores `separate`.
3. **Contract evaluation itself races on shared collections** — rate_limiter.e 40-42 (`counts_model` iterates `counts`), invariant 142 `never_over` iterates `counts`; event_bus.e 34-36, invariant 106; poll_waiter.e 154. `subscribe`'s precondition `not_yet: not subscribers_model.has (…)` (58) is evaluated by a handler thread with no lock while another `subscribe` may reallocate the list — every long-poll subscribes/unsubscribes, so this is steady state; invariants iterate collections that `record` resizes → torn reads, crashes caused by assertion monitoring. → every model/contract-support query of a locked object acquires its lock; invariants keep scalar clauses only; move `never_over` into `record` as a `check` under the lock; bodies holding the lock must not call the locking queries (EiffelBase MUTEX not documented re-entrant).
4. **wait_for_events forbids the very thing it waits for** — chat_service.e 189 `nothing_appended: store.last_event_id = old store.last_event_id`: on the success path another thread has appended; satisfiable only on the timeout path. → delete.
5. **authenticate's `failure_counted` is unsatisfiable at the lockout boundary** — chat_service.e 69 vs rate_limiter.e 107 (`record` requires `is_allowed`) and invariant 142: the 11th attempt must fail and be counted to 11 while `record` refuses at 10. Also the per-IP key (`login_ip_key`, 324) is promised in the comment but in no clause. → `failure_counted: (not Result.is_success and old limits.is_allowed (…)) implies limits.count (…) > old …`; add `ip_locked_out_stays_out` and `ip_failure_counted`.
6. **create_user / create_bot `unique_or_error` is an equality** — chat_service.e 248, 263: a fresh username must succeed, so a store error, a full disk, or the Phase 1 501 stub violates the postcondition; two concurrent admins creating the same name both capture `old has_username = False`. → `duplicate_refused` + `success_is_fresh` as implications.
7. **RATE_LIMITER.record's precondition makes check-then-record racy and forbids the atomic form** — rate_limiter.e 104-114, 142: two threads at limit-1 both pass `is_allowed`, both record → limit+1 → `never_over` fails. → `try_record (a_key): BOOLEAN` deciding and counting under the lock; `is_allowed` advisory only.
8. **One window for the whole limiter cannot express per-minute / per-10-minute / per-hour** — rate_limiter.e 20-24 (`make (a_window_seconds)`), 92; simple_chat_server.e 23 `create limits.make (3600)`; server_config.e 97-99. 30 posts/minute becomes 30/hour or 1800/hour; lockout lasts an hour. → `set_limit (a_prefix, a_limit, a_window_seconds)`, `windows_model`, `window_for`; facade `start` ensures each configured pair.
9. **A limiter that never limits passes every contract; no rate-limit test** — rate_limiter.e 67-69 (`limit_for` ensures only positive/default), chat_service.e 109 (`rate_limited` vacuous when `is_allowed` is always True), chat_assault.e 414-453 (no lockout test). → `matching_prefix (a_key)` + `limit_for` ensure `by_prefix`; `post_message` ensure `recorded_on_success`; Phase 5 tests `test_post_rate_limit_refuses_past_the_limit`, `test_login_lockout_boundary`.
10. **EVENT_BUS.ring's frame contradicts its own raise-handling rule and the long-poll subscribe pattern; `unsubscribe`'s precondition turns that into a second exception** — event_bus.e 7, 84, 93, 67; chat_service.e 185. A raising subscriber must be removed (then `subscribers_unchanged` fails); a handler may subscribe mid-ring; after auto-removal the owner's `unsubscribe` violates `present` → 500 to a client; the bus has no logger so "logged" cannot be honoured. → drop the frame; idempotent `subscribe`/`unsubscribe` with `added`/`removed` postconditions; give the bus a CHAT_LOG; catch only non-assertion exceptions.
11. **SSE_STREAM.deliver_pending compares a per-room cursor with a store-wide id** — sse_stream.e 78 `caught_up_or_closed: last_delivered_id >= store.last_event_id or else not is_open`; with two rooms every correct implementation fails. → `store.count_after (room_id, last_delivered_id) = 0` at best; better a `delivered_model` and single-threaded catch-up tests.
12. **SSE_STREAM.open's documented plan (replay inside open) violates the inherited `starts_at_since`** — sse_stream.e 64 vs event_source.e 42. → `open` sets state + preamble only; the handler calls `deliver_pending`.
13. **SSE_STREAM has no lock and does client I/O on the poster's thread** — sse_stream.e 81-87, 73-79, 94-102, 129-133; event_bus.e 5-7. Two concurrent wakes → duplicate pages out of order; heartbeat from a timer interleaves bytes; a slow client's TCP back-pressure stalls every poster (snapshotting the subscriber list avoids the bus lock, not the synchronous call-out). → `wake` only flags + broadcasts (embed a POLL_WAITER); the owning handler thread loops wait → deliver/heartbeat; one thread per STREAM_SINK. The dispatcher needs the same treatment.
14. **login_user_key calls `to_string_8` on arbitrary user input** — chat_service.e 321 `a_username.as_lower.to_string_8` (precondition `is_valid_as_string_8`), used inside `old` at 68-69: a Cyrillic username raises from unauthenticated input. → `{UTF_CONVERTER}.utf_32_string_to_utf_8_string_8 (a_username.as_lower)`; refuse invalid usernames with a 401 result before any lookup; add `bots_and_inactive_refused`.
15. **Token revocation is uncontracted end to end** — chat_service.e 296-301 (`revoke_bot_token`, no ensure), chat_store.e 305-310 (`remove_sessions_of`, no ensure), reset_password 275; MEMORY_CHAT_STORE states `none_left` privately (344). A no-op passes everything; no revocation test. → `CHAT_STORE.has_session_of`; ensures `none_left`, `revoked`, `sessions_revoked`; Phase 5 `test_revoke_bot_token_denies_the_next_request`.
16. **PASSWORD_HASHER.hash's `never_plaintext` is false for legal short passwords** — password_hasher.e 29-30, 37: `hash ("0")` fails deterministically because the iterations field "600000" contains "0". → precondition `Minimum_characters = 8` or condition the clause; note it is probabilistic.

## MEDIUM (17)
STREAM_SINK.write's `open` precondition and exact byte count cannot survive a peer that disconnects mid-stream (stream_sink.e 31-35; sse_stream.e 51-54, 96-101; web_stream_sink.e 40-44) → `counted_when_open`/`closed_stays_closed`, heartbeat without `open`. POLL_WAITER.wait mis-accounts time (deducts a full 250 ms slice regardless) and ignores the statuses it is broadcast for (poll_waiter.e 91-94, 133) → clock-based deadline, exit on statuses, drop `l_slept`. wait_for_events cannot return the statuses the API promises; waiter lifetime/cleanup unspecified (chat_service.e 171, 182-185; chat_api.e 57-59) → return CHAT_PAGE-like tuple, per-call waiter, unsubscribe in a rescue. POLL_WAITER.statuses is the internal list, exported mutable, read across threads, no model (poll_waiter.e 50, 132, 70) → `{NONE}` + `statuses_snapshot` + `statuses_model` under the lock. CHAT_SERVICE room preconditions weaker than the store's (`is_stored` vs `has_room`) → `room_known: store.has_room (a_room.id)`. post_message/post_image do not tie the returned event to their inputs; post_image bypasses the post limit; `e.attachment = a_attachment` is reference equality the SQLite store cannot honour → `right_event`, `rate_limited`, `recorded_on_success`, `same_attachment` on append_event by id. post_system/publish_status under-contracted → monotone append/ring clauses, `right_room`, `from_stored`, EVENT_BUS `last_status`. session_for_token has no "right session" clause (issuer hidden) and `now` moves → `token_hash_of` exported, `right_one`, `old now`. `last_error` never cleared → `is_running xor (last_error /= Void)` fails on a second start after a failed one (chat_web_app.e 54, simple_chat_server.e 111, front_door.e 65/79) → clear on start or weaken. RATE_LIMITER.set_limit can break `never_over`; `is_allowed.definition` and `count` purity time-fragile → precondition or drop `never_over`; `count` pure, pruning in `record`/`prune`. CHAT_LOG never promises what was written was redacted; secret-field rule targets `password=` while the wire is JSON `"password":` (chat_log.e 26-45, 84) → `last_line` + `redacted` ensure; rule matches `password|token|hash` + optional quote/spaces + `=`/`:`. client_ip / trusts_forwarded_headers carry no trust contract; XFF list handling and header `to_string_8` unspecified (chat_web_app.e 85-104) → `peer_when_untrusted`, `rightmost_when_trusted`, `definition` on trust, `is_valid_as_string_8` guard, case-insensitive `Bearer`, hex-64 token. SERVER_CONFIG exports its mutable lists (`participants`, `validation_errors`) — invariants and `is_valid` bypassable; handle uniqueness case-sensitive vs a case-insensitive parser → `{NONE}` lists, read-only accessors, `as_lower` comparisons. Door and DNS never tied to the config they must agree with → `door_matches_config`, `dns_matches_config` in `start`. CHAT_STORE.events_before does not say which page; update_user does not say the row now matches; reset_password's `verifiable` checks the in-memory user → `count_before`, `nearest`, `newest_first`, `written`, ensure against `store.user`. "Each exactly once" nowhere contracted for EVENT_SOURCE → `delivered_model` with `strictly_increasing`, `starts_after_since`, `extended`. CHAT_SERVICE puts user-controllable facts in preconditions while promising never to raise for a user mistake (`member`, `within_limit`, `body_given`; CHAT_API has no contracts) → either CHAT_RESULT outcomes for user-facing rules or a per-handler guard note + a contracted `reply` helper. ADDRESS_PARSER edge cases (`via train`, `@claude,`, `@claudette`, bare `@claude`) → `via_shape`, `handle_lowercase`, `handle_no_blank`, `via_known`, `empty_is_plain`. PASSWORD_HASHER.make never sets the iteration count it guarantees (`floor_applied` depends on simple_encryption's default) → pin explicitly.
