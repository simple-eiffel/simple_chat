1. THE SYMPTOM, AS REPORTED
--------------------------------------------------------------------------------

From Larry's live sw_session.log (one ~20 minute session): 13 stalls,
211.6 s frozen in total - 8.3 8.9 9.1 9.9 13.4 14.5 14.7 16.2 21.5 21.9 23.7

The stored messages prove the stalls COST INPUT, not just time: one message cut

that stops pumping for about five seconds: it ghosts it, discards the keystrokes
aimed at the ghost, and lets held keys auto-repeat into a burst when the real
window wakes. Nothing an application can buffer gets that back. A fix that
merely SHORTENS the stall is therefore a failing fix.

3. WHAT IT WAS: THE ROOT PROCESSOR'S ALLOCATOR
--------------------------------------------------------------------------------

The same live run, with one addition: a pure allocation burst on the root
(200 x 1 KiB strings into a fresh list), touching nothing of the client's,
timed beside the heartbeat.

  tick   worst          3 ms
  ALLOC  worst     21 060 ms      <-- the freeze

The stall is not in the presenter, the inbox, the view or the transport. It is
in ALLOCATING MEMORY.

ISE's garbage collector stops every thread in the system before it collects. A
thread that is inside a plain `external "C inline"' call is where the runtime
cannot see it and cannot stop it, so the collection waits for that call to
return - and every other processor waits with it, at its next allocation.

SIMPLE_WINHTTP.c_send (D:/prod/simple_winhttp/src/simple_winhttp.e:521) is
declared

    external "C inline use %"simple_winhttp.h%""

with NO `blocking' marker (grep -c blocking simple_winhttp.e = 0). One exchange
- the whole of a 25 second long poll - is spent inside it. So while the poller
holds the connection open, the GUI thread freezes at its very next allocation:
a string, an MML sequence built by a postcondition, a shaped line.

Two probes separate the two ways a processor can wait (FREEZE_ASSAULT, GC_PROBE).
Same processor, same duration, nothing else running:

  a processor asleep 9 000 ms through EXECUTION_ENVIRONMENT.sleep
      worst allocation on the root:        1 ms
  a processor inside a blocking C call, 3 000 ms at a time
      worst allocation on the root:    7 931 ms

EXECUTION_ENVIRONMENT.sleep is marked for the runtime and costs the GUI nothing.
An unmarked C call costs it the whole wait. That is the entire defect.

COROLLARY, and it matters: moving blocking work OFF the GUI processor does not
help, because the collector stops the GUI wherever the blocking call is issued.
Only shortening the call helps. The floor for this client is therefore ONE HTTP
exchange, wherever that exchange is made.

4. THE FIX
--------------------------------------------------------------------------------

src/client/event_poller.e - ONE body change and ONE added constant. No `require',
`ensure', `invariant' or signature was touched anywhere in src/.

  ADDED  EVENT_POLLER.Poll_slice_seconds: INTEGER = 0
         How long ONE exchange may keep the poller inside the transport. The
         constant carries the whole explanation above in its comment, including
         the one-line upstream change that would give the long poll back.

  BODY   EVENT_POLLER.run:  poll_once ({CHAT_CLIENT}.Max_wait_seconds)
                        ->  poll_once (Poll_slice_seconds)

         `poll_once's precondition `seconds_in_range: a_wait_seconds >= 0 and
         a_wait_seconds <= {CHAT_CLIENT}.Max_wait_seconds' is satisfied by 0, so
         the contract stands unchanged and is not weakened.

  NOTES  EVENT_POLLER's and CLIENT_APP's class notes no longer promise a 25 s
         block; both now say what one exchange costs and why.

WHY ZERO AND NOT A SHORTER SLICE. CHAT_REQUEST_HANDLER.handle_wait holds the
doorbell only while `seconds' > 0 (`if l_reply.is_empty_page and l_seconds > 0'),
so `seconds=0' is answered at once and the exchange lasts one round trip. Any
positive slice leaves the poller inside C for that slice: measured on the
scripted wire, a 2 s slice still stops the root's allocator for 892 ms, and 1 s
would still be ~500 ms - over the frame budget, and over the ~5 s ghosting
threshold only at 25. Zero is the only value that bounds the stall by a round
trip rather than by a held connection.

WHAT IT COSTS. The doorbell, for the first message into a room that has gone
quiet: `pause_seconds' is `Quiet_floor_seconds' (1 s) from the second quiet poll
in a row, so that first line can arrive up to a second late. Everything after it
is immediate again - a page resets `quiet_polls' and `pause_seconds' is 0 once
more, so a conversation runs at the round trip. The quiet-room poll rate is one
request per second per member; CHAT_WEB_APP.Max_connections is 64.

THE PROPER FIX, WHICH IS NOT IN THIS REPOSITORY (reported, not done):
mark SIMPLE_WINHTTP.c_send `blocking' so the runtime releases the collector
across it. Then `Poll_slice_seconds' can go back to
{CHAT_CLIENT}.Max_wait_seconds and the long poll returns with no stall at all.
That is a change to D:/prod/simple_winhttp, outside this cycle's scope.
