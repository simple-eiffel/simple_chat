--- STUB 1: CHAT_CLIENT.post_image (src/client/chat_client.e) ---------

Was: `create Result.make_error (... Code_not_implemented, "Not implemented
(Phase 1 skeleton)", 501)`.

Now: one exchange, shaped exactly as CHAT_REQUEST_HANDLER.handle_post_image
reads it.

  POST /rooms/{id}/images
  Authorization: Bearer <64 hex>          (authorized_headers, as everywhere else)
  Accept: application/json
  Content-Type: application/octet-stream  (the body is opaque bytes, not JSON)
  X-File-Name: <percent-encoded UTF-8>
  X-Caption:   <percent-encoded UTF-8>
  <body> = the SPECIAL [NATURAL_8] verbatim

  timeout 60 s (`Upload_timeout_seconds`), not the 15 s a message gets: an image
  is up to the server's upload_bytes (8 MiB by default) on one exchange.

  The 201 is decoded through CLIENT_CODEC.event exactly as post_message decodes
  its echo; an event for another room or of another kind is a 502 result, a 4xx
  carries the server's own error, a transport failure is 503. The two existing
  ensures (`image_on_success`, `echoed`) hold; neither they nor `session_kept`
  were touched.

  New {NONE} helpers: `image_headers` (with its own postconditions naming every
  header it sets) and `byte_string`.

BYTE FIDELITY OF THE BODY - verified in the library, not assumed.
  D:/prod/simple_winhttp/src/simple_winhttp.e, `send`, lines ~212-227:

        -- The body is marshalled byte-for-byte: C_STRING would
        ...
      if attached a_body as la_body and then not la_body.is_empty then
          l_body_len := la_body.count
          create l_body_area.make (l_body_len)
          ... l_body_area.put_natural_8 (la_body.code (i).to_natural_8, i - 1)

  It copies `code (i)` into a MANAGED_POINTER rather than handing the string to
  C_STRING, so every value 0..255 - the zero byte included - reaches the wire.
  A STRING_8 body is therefore byte-faithful; no re-encoding, no truncation at
  a NUL. `byte_string` states `sized`, `first_byte_kept`, `last_byte_kept`; the
  full per-byte equality is proved in the assault instead of asserted per call,
  because a per-byte postcondition would walk a whole image on every upload.

--- The header encoding: a NEW shared class, and one server-side read ------

  NEW: src/domain/chat_header_text.e (CHAT_HEADER_TEXT)
       `encoded (READABLE_STRING_GENERAL): STRING_8`  - UTF-8, then percent-
            encode every byte outside RFC 3986's unreserved set
       `decoded (READABLE_STRING_8): STRING_32`       - the inverse, tolerant
       `is_wire_clean`, `is_unreserved`, `is_hex_digit` (contract support)

  WHY it is needed: a header value may carry printable ASCII and nothing else.
  WINHTTP_TRANSPORT.send refuses a request outright - before a byte leaves the
  machine - when `SIMPLE_WINHTTP.is_header_table_clean` is False, and that query
  admits only codes 32..126. Raw UTF-8 in X-Caption would therefore never have
  reached the server over the real transport: the client would have answered a
  transport failure for every non-ASCII file name or caption.

  Both sides use the one class (Single Choice): CHAT_CLIENT writes with
  `encoded`, CHAT_REQUEST_HANDLER.header_32 reads with `decoded`. `decoded` is
  tolerant on purpose and cannot raise - a value with no percent sign comes back
  as plain UTF-8, so a hand-made request with an ASCII name still works, and a
  percent not followed by two hex digits stays a percent.

  SERVER-SIDE CHANGE (reported, not slipped in - no contract touched):
    src/web/chat_request_handler.e `header_32` now percent-decodes before the
    UTF-8 decode. It is a {NONE} implementation helper with no require/ensure;
    nothing else in the project calls it; no route, reply or contract changed.
    Behaviour is a strict superset for anything already working (no '%' -> same
    answer as before).

--- A REAL DEFECT FOUND IN simple_web (worked around here, NOT fixed there) --

  `SIMPLE_WEB_SERVER_REQUEST.header` (D:/prod/simple_web/src/server/, line ~218):

      l_header_name := "HTTP_" + a_name.to_string_32.as_upper.to_string_8
      ... al_l_request.meta_string_variable (l_header_name)

  It upper-cases and prefixes, but does NOT turn hyphens into underscores, which
  is what CGI (RFC 3875 4.1.18) requires of a meta-variable name. So `header
  ("X-File-Name")` asks for HTTP_X-FILE-NAME and can never match the real meta
  variable HTTP_X_FILE_NAME. Every hyphenated custom header is invisible to this
  query. Nothing had caught it because the only header simple_chat read before
  today was "Authorization", which has no hyphen.

  PROVEN, not deduced: with the handler asking for "X-File-Name" the live server
  answered with an EMPTY caption and file name (transcript: `name and caption
  came back MANGLED ()`); with the handler asking for the CGI meta spelling
  "X_File_Name" the same live post answered `byte for byte (shalom + robot)`.

  Worked around inside this repo only, as instructed: `handle_post_image` now
  asks for `Meta_file_name` = "X_File_Name" and `Meta_caption` = "X_Caption",
  with a comment naming the wire headers (still X-File-Name / X-Caption) and the
  library defect. NO file outside D:/prod/simple_chat_wt_stubs was modified.
  -> simple_web should be fixed upstream: convert '-' to '_' in `header`.

2. THE ADDITIVE STORE FEATURE (the one thing that had to be added)
=====================================================================

src/store/chat_store.e, feature -- Lifecycle:

    backup_to (a_path: READABLE_STRING_32): BOOLEAN
        require
            open: is_open
            path_given: not a_path.is_empty
            fresh: not is_file_at (a_path)
        deferred
        ensure
            written: Result implies is_file_at (a_path)
            nothing_left_behind: not Result implies not is_file_at (a_path)
            still_open: is_open
            data_untouched: last_event_id = old last_event_id
                and event_count = old event_count
                and user_count = old user_count and room_count = old room_count
                and session_count = old session_count
                and attachment_count = old attachment_count

and, in the same class, the contract support the ensures speak of (effective,
so both heirs answer it identically):

    is_file_at (a_path: READABLE_STRING_32): BOOLEAN
        -- Is there a file at `a_path'?

EFFECTED IN BOTH STORES:

  SQLITE_CHAT_STORE.backup_to - `active_db.perform_with ("VACUUM INTO ?", ...)`,
    the same statement `open` already uses to back a behind-version file up
    before migrating: SQLite reads the database through the very connection that
    holds it, so nothing has to pry a locked file open (a plain file copy on
    Windows cannot), and what lands is one consistent, defragmented database
    with the WAL folded in - not a file plus two companions. Wrapped in
    rescue/retry; a failed or empty copy is deleted through `discard_file`
    (itself rescue-guarded), so `nothing_left_behind` holds even when the delete
    is the thing that fails.

  MEMORY_CHAT_STORE.backup_to - an empty body (Result stays False), with
    `ensure then never: not Result; nothing_written: not is_file_at (a_path);
    models_untouched: ...`. The oracle keeps its rows in memory; writing a
    hand-rolled dump would make it claim a backup a restart could not read back.

NOTHING ELSE IN THE STORE OR SERVICE CONTRACTS WAS TOUCHED. `git diff
src/store/chat_store.e` is additions only - no existing require, ensure,
invariant or signature was modified anywhere in this branch. No item had to be
STOPPED.
