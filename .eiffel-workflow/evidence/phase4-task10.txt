3. WHAT COULD AND COULD NOT BE EXERCISED HEADLESS
--------------------------------------------------------------------------------

COULD, and was. SW_WINDOW.make allocates a cairo image surface and a painter and
creates NOTHING native; only `run' calls shell_run. So both windows are built
offscreen in the suite and driven exactly as a member drives them:

  - three events -> three bubbles -> three ids in order, with the roles the
    thread will draw them with (mine right, system centred, theirs left)
  - an image event -> a marked, named, sized, captioned attachment line
  - the badge, the ephemeral line (replaces, never stacks), the error line
    (kept in order), the connection state - and the law that none of them
    disturbs the events
  - is_foreground False with no native window, before and after showing
  - the window's SW_SHAPING kit laying out the D-015 acceptance line:
    3 runs, base_direction RTL, first run LTR (the Greek, leftmost), last run
    RTL (the Hebrew, rightmost), every character covered, total_height 25
  - Enter submits, an empty line goes nowhere, an ordinary character types
  - CHAT_PRESENTER against the REAL pane with a REAL EVENT_INBOX: two events in
    order, unread counted twice and the tray notified twice (because a pane with
    no window is not in front - the honest answer AND the interesting branch),
    a status that is not an event, a garbage page that is an error and not an
    exception
  - the door's three refusals (non-https stranger, empty/spaced name, empty
    password) before a byte leaves the PC, the host's refusal message, and an
    acceptance
  - CLIENT_APP's decision tree over a scripted transport: a sealed blob that
    GET /me honours means no password (and the request really is GET /me); no
    blob means the door; a 401 comes back as the server's own message; a good
    password opens the session; a plain-http stranger is refused with zero
    exchanges beyond the locator's one probe; the first room is opened, named,
    rostered and polled, and `tick' keeps the badge equal to the presenter's
    count; a server that lists no room leaves the room closed and the reason on
    the pane's error line.

COULD NOT, and is honestly left to the console:

  - PIXELS. Nothing is painted until `run', and `run' needs an interactive
    desktop. No SKIP was needed anywhere - every headless test really runs -
    but the three visual properties of the acceptance line are RUNBOOK.md's.
  - The tray BALLOON itself (SHELL_TRAY degrades to silence with no shell; the
    counts still hold exactly, which is what TRAY_NOTIFIER's contracts promise
    and what the Task 9 test already proves).
  - Resize behaviour (R10: re-layout at the drag's END). SW_CHAT_THREAD's own
    debounce is assaulted in simple_widgets; here it is a runbook step.

7. NOTES A LATER READER WILL WANT
--------------------------------------------------------------------------------

ONE NATIVE WINDOW AT A TIME. simple_shell keeps a single module-global
s_shell_hwnd, so the door and the room pane can never be up together. `run'
therefore runs the door, lets it CLOSE, and only then runs the pane. WM_DESTROY
posts WM_QUIT, GetMessage consumes it and returns 0, and a second shell_run
registers the same window class again (RegisterClassW's failure on an existing
class is ignored and CreateWindowExW still succeeds), so the sequence works.
This is also why a lost session is handled by CLOSING the pane and going round
the loop rather than by opening a dialog over it.

WHY THE PRESENTER IS SOMETIMES REBUILT. CHAT_PRESENTER binds to one CHAT_CLIENT
for its life, and pointing the door at a different server needs a new endpoint
and therefore a new client. `attempt_login' rebuilds both. Nothing else holds
the presenter - `tick' reads the attribute at call time - so the swap is safe,
and it can only happen while no room is open.

VOID SAFETY AND AGENTS. An agent on Current lets Current escape, so every
attribute must be set before one is made. Both windows therefore build their
whole widget tree first and wire `on_click' / `on_submit' LAST. The first
compile failed on exactly this (VEVI, attributes send_button and root).

THE FOREGROUND QUESTION. CHAT_PRESENTER's whole unread law turns on
CHAT_VIEW.is_foreground, and simple_shell raises no activation event and is not
this project's to change. SW_CHAT_VIEW asks Windows directly - one inline C
external, GetForegroundWindow() against its own hwnd - and answers False
whenever there is no native window, which is both the honest answer and the
branch the headless assault drives.

INDIRECT LIBRARIES ARE NOT IN THE UNIVERSE. simple_widgets includes
simple_shaping, but SHAPED_LAYOUT / SHAPED_LINE / SHAPING_CONSTANTS were VTCT
"unknown class" from this system's own clusters until simple_shaping was named
explicitly in the ECF. Worth knowing before the next library adopts another.

THE C-PHASE HAZARD DID NOT BITE. simple_shell/Clib/simple_shell.h declares a
local named `small' (a Windows SDK macro) which has broken the C phase of some
release builds. All four targets finalized here without a C2059. Nothing in
simple_shell was edited.
