# Phase 2 Synopsis — simple_chat adversarial contract review

Date: 2026-08-29 · 86 classes reviewed by four parallel cluster reviewers; every HIGH re-read against the source by the orchestrator · Full findings: `evidence/phase2-claude-response.md` (38 HIGH · 53 MEDIUM · ~30 LOW) · Implementation sketch: `approach.md`

## Overall assessment: **FAIL as written — the architecture passes, the contracts do not**

The design holds: doorbell bus, store as the single truth, swappable seams, thick client over a JSON API, argv-only tools. Nothing in 86 classes argues for a redesign. But the contracts were written for a single thread and the server runs one thread per connection; several are unsatisfiable by any implementation; and five security properties the design *claims* are not written down anywhere an implementation would have to honour them. Implementing against these contracts would produce a system whose assertions fire on correct code under load and stay silent on the bugs that matter. Phase 3 must wait for a contract-repair pass (a Phase 1b), then a targeted re-review of the repaired clusters.

## Five decisions only Larry can make

- **D1 — The concurrency model. DECIDED (Larry, 2026-08-29): SCOOP.** Consequences, in full in `approach.md` §8: one `separate CHAT_SERVICE` processor owns the store, bus, limiter and log, so every exact postcondition (`= old + 1`) is correct as written and `is_allowed`-then-`record` is atomic; per-request `separate POLL_WAITER` + `ALARM` with a SCOOP wait condition replace MUTEX/CONDITION_VARIABLE; `EVENT_BUS.ring` becomes asynchronous separate commands, so posters never stall and no subscriber can re-enter itself; the client gets a `separate` poller and a `separate` inbox. Findings 1–10 are absorbed by that restructuring. The 2026-08-29 spike found simple_web did not compile in SCOOP mode (four VFFD(8) on `once ("PROCESS")` singletons); **fixed the same day in simple_web 0.2.0** (`SIMPLE_WEB_HANDLER_SERVER [H]`, per-request handler class; proof target serves two concurrent requests). simple_chat's ECF is now `use="scoop"`: zero warnings, 30/30.
- **D2 — Subscribers never work on the ringing thread.** Answered by D1: separate commands are asynchronous and a processor runs its wakes one at a time. What remains from Issue 9 is design, not threading: per-room cursors on the dispatcher, an idempotent `handle_event`, and an `answered_model` for exactly-once. (Issue 9)
- **D3 — `@claude`'s sandbox.** Today's design runs `claude -p` in the vault so skills and memory load, and posts whatever `image_path` the model names. That hands anyone who can type `@claude` the vault's private notes and any image on the host. Recommendation: a dedicated working directory with a curated CLAUDE.md and chosen skills (not the vault, not MEMORY.md), tools disabled, `image_path` fenced to `<data>/participants/<handle>/` by contract. This changes what `@claude` can know; it is your call. (Issue 33)
- **D4 — The marker authenticates.** Today 🤖 decorates bots but does not authenticate them: a bot draft with `is_bot_authored = False` posts unmarked, and a person may begin a message with 🤖. Recommendation: `bot_flag_truthful` on `append_event` (the flag must equal the sender's `is_bot`) and `humans_unmarked` on `post_message`. Cheap, and it makes "no path through the system" true. (Issue 35)
- **D5 — Oracle semantics.** The memory store keeps the caller's objects; SQLite necessarily copies. A forgotten `update_user` passes every oracle test and loses the deactivation in production. Recommendation: the oracle stores and returns twins, and the deferred contract says what persists. (Issue 23)
- (D6, minor) User-facing rules — not a member, body too long, empty body — as CHAT_RESULT outcomes rather than preconditions, so the API layer does not have to re-implement them; preconditions stay for programmer errors only.

## Critical — must fix before implementation (38 HIGH, by theme)

**Concurrency (1–10):** exact/unchanged postconditions on shared state across CHAT_SERVICE, EVENT_BUS, CHAT_LOG, RATE_LIMITER, STREAM_SINK, CHAT_STORE and the oracle's frames · contract evaluation iterating shared collections without the lock (limiter, bus, waiter, poller) · POLL_WAITER's postconditions evaluated after unlock · EVENT_POLLER `older_kept` and its extend-before-cursor order · `wait_for_events` forbidding the append it waits for · `RATE_LIMITER.record`'s check-then-act precondition (→ `try_record`) · `add_user`'s `fresh_username` with no UNIQUE in the schema · subscribers working on the ringing thread (dispatcher, SSE) · EVENT_BUS.ring's frame vs its own raise-handling; `unsubscribe`'s precondition.

**Wrong by construction (11–27):** login lockout boundary unsatisfiable, per-IP key uncontracted · `unique_or_error` as an equality · one limiter window for three policies · a limiter that never limits passes; no lockout test · the dispatcher's rate limit absent; `always_answers` self-counted · restart replays history (`cursor = 0`) · SSE `caught_up` compares a room cursor with the global id; SSE `open` plan vs `starts_at_since` · `events_since` not gap-free on a full page (lost messages) · `events_before` satisfied by the oldest N · duplicate memberships vs the relation model · client `post_message.echoed` asserts the server's honesty · oracle reference semantics · image events with an unstored attachment · `never_plaintext` false for `"0"` · no runtime bound on the Ollama engines · `no_orphan` satisfiable by forgetting the child.

**"Never raises" broken (28–30):** the decoder violates `CHAT_ERROR.make`'s preconditions on a captive-portal 200, a 302, or an empty message · non-Latin-1 wire fields and usernames reach `to_string_8` (precondition verified in EiffelBase) · `created_at` unvalidated (`make_from_iso8601` verified to have no validation).

**Security (31–38):** the argv gate is vacuous whenever a query shaper is configured and records nothing of what ran · `via` ignored by the gate and the disclosure · `@claude` in the vault + unfenced `image_path` (D3) · `uploads/../../x.png` passes the attachment invariant (path traversal) · unverified bot flag / forgeable marker (D4) · `http://localhost@evil.example` passes the loopback test and receives the Bearer token in clear; nothing forbids Bearer on an insecure endpoint · token revocation uncontracted end to end · `is_safe_argument` unspecified (empty, controls, a leading `-`).
